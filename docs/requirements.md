# Requirements: doc-sync-agent

## Overview

Implement US-101 as a TypeScript CLI that deterministically generates and synchronizes repository documentation from verifiable repository evidence. It supports local git repositories and public GitHub repositories, preserves manually maintained README content, tracks committed changes, and records documentation updates in a changelog. Information without repository evidence is reported as "Not Found"; no AI services are used.

Source: docs/user-story.md, the user's eight clarification answers, and the subsequently requested v1 defaults below.

## Functional requirements

- **FR-1 - Inputs:** Accept a local repository path or a public GitHub repository URL. Reject private repositories with a clear error; private-repository access is not supported in v1.
- **FR-2 - Validation:** Validate all external input, including paths, URLs, CLI arguments, and persisted sync state, with zod before using it. Missing or invalid input shall produce a clear error and a nonzero exit status without modifying output files.
- **FR-3 - GitHub acquisition:** Full-clone a public GitHub repository, without depth limits or history filtering, into a temporary directory on each run so baseline-to-HEAD diffs can use its history. Use its default branch unless the user supplies `--branch`; when supplied, use that branch. An unavailable repository or branch shall produce a clear error. Remove the temporary clone on success or handled failure, including dry runs; report cleanup failures without exposing temporary file contents.
- **FR-4 - Local output for URLs:** Require `--out` for GitHub URL input. Persist only `README.md`, `CHANGELOG.md`, and `.docsync.json` directly in that directory, not a repository copy. Accept an absent or empty directory, or an existing directory whose valid sync state matches the normalized repository URL and selected branch; reject other nonempty directories without modification. Create an absent directory only during a successful non-dry-run write. Reuse matching output documentation to preserve manual content; on first use, seed it from the committed repository README and changelog if present. Do not create remote commits or pull requests. `--out` and `--branch` are URL-only options; reject them for local input.
- **FR-5 - Repository scan:** Inspect eligible tracked source, supported manifests, configuration files, and any existing committed README at HEAD. Scan manifests recursively; root manifests take precedence, followed by nested manifests in ascending repository-relative path order, with `/` separators. Apply the exclusions in NFR-2 and security restrictions in FR-24 and FR-25. Do not follow symlinks or read files outside the repository. Refuse symlinked output files or directory components before writing.
- **FR-6 - Stack detection:** Recognize Node.js/TypeScript from `package.json`, Python from `requirements.txt` or `pyproject.toml`, Java/Maven from `pom.xml`, and Go from `go.mod`. List every detected supported stack in a multi-stack repository. Report unsupported or unidentified stacks as "Not Found" rather than inferring a stack without supported evidence.
- **FR-7 - README sections:** Generate sections named Project Name, Purpose, Tech Stack, Setup/Install Steps, Usage, Project Structure, and Environment Variables. Each section shall use repository evidence or the explicitly approved setup mappings in FR-9; unavailable information shall be "Not Found". For Project Name, select the first nonempty manifest name using FR-8's ordering (`name`, `[project].name`, `[tool.poetry].name`, Maven `name` then `artifactId`, or Go module path); otherwise use the first level-one heading outside generated markers in the committed README; otherwise output "Not Found". Project Structure shall be a sorted listing of eligible repository-relative file paths. No project facts shall be guessed.
- **FR-8 - Purpose precedence:** Select the first nonempty description using root manifests before nested manifests, then ascending directory path, and within each directory `package.json`, `pyproject.toml`, `pom.xml`, `go.mod`, `requirements.txt`. Supported description fields are package `description`, Python `[project].description` then `[tool.poetry].description`, and Maven `description`; do not infer descriptions for Go or requirements files. Otherwise use the first prose paragraph outside generated markers in the committed README, skipping headings, lists, tables, comments, fenced code, and image/badge-only paragraphs; join its lines with spaces. Otherwise output "Not Found".
- **FR-9 - Setup mappings:** Generate `npm install` for `package.json`, `pip install -r requirements.txt` for `requirements.txt`, `mvn install` for `pom.xml`, and `go build` for `go.mod`. For a multi-stack repository, include the applicable approved commands with their manifest directories, in scan order, deduplicated per directory and command. A Python project with only `pyproject.toml` shall have setup reported as "Not Found"; do not guess its package manager.
- **FR-10 - Usage precedence:** List package script names as `npm run <script>` and declared executable/bin names in scan order, with their manifest directories; do not copy script bodies. If no manifest usage is found, copy the first committed README section whose ATX heading text equals `Usage` case-insensitively, outside generated markers, through the next heading of equal or higher level. Otherwise output "Not Found". Sanitize all extracted content under FR-25; do not invent commands or script names.
- **FR-11 - Generated markers:** Wrap each generated section in matching comments of the form `<!-- docsync:start name -->` and `<!-- docsync:end name -->`. The canonical names, in section order, are `project-name`, `purpose`, `tech-stack`, `setup`, `usage`, `project-structure`, and `environment-variables`. Reject unknown, duplicate, nested, unmatched, or out-of-order start/end marker pairs as fatal errors without modifying files; valid section pairs may appear in any section order.
- **FR-12 - Manual preservation:** Never replace or edit existing README content outside generated markers. Preserve existing line endings and manual bytes; use LF for a new README. Append each missing marked section in canonical order, including when a README has some markers or a valid baseline but no source changes. An unmarked manual heading does not count as a generated section. On the first run against a README without markers, preserve all existing content and append all generated sections. If no README exists, create one containing the required generated sections.
- **FR-13 - Incremental updates:** With a valid baseline, update only generated sections impacted by eligible committed changes, plus missing sections under FR-12. A supported manifest change impacts Project Name, Purpose, Tech Stack, Setup/Install Steps, and Usage. A manual README change impacts Project Name, Purpose, and Usage. A `.env.example` or other source/configuration change impacts Environment Variables; manifest changes also impact Environment Variables because source references can occur there. Any eligible file addition, deletion, or rename impacts Project Structure. Apply the union for multiple changes, considering both old and new paths for renames. Preserve unaffected sections and manual content; report impacted names. Ignore `.docsync.json` and `CHANGELOG.md` in all directories, and compare README changes after removing generated marker blocks, so generated-document-only commits do not trigger sync entries or Project Structure changes.
- **FR-14 - Baseline state:** Record the last successfully synced commit SHA in `.docsync.json` at the local target repository root, or directly in `--out` for URL runs. URL state shall also record the normalized repository URL and resolved branch name for identity validation. Use the SHA as the next baseline. Advance it after every successful normal run, including runs with no relevant changes; do not advance it on dry runs or failures.
- **FR-15 - Committed changes only:** Compute changes using `git diff <last-sha>..HEAD`. Use committed content at HEAD for source extraction and generation; staged, unstaged, and untracked source changes shall not affect generated documentation. Read current destination README/changelog files only for preservation and marker-based merging, never as new extraction evidence. When the local working tree is dirty, warn that uncommitted source changes are ignored; preserve manual destination edits under FR-12.
- **FR-16 - Full-scan fallback:** If no baseline has been recorded, perform an initial full scan. If a recorded baseline commit is missing or unavailable despite the full clone, warn and perform a full scan without a second fetch/deepening attempt; apply the same fallback to local repositories with unavailable history. Never terminate solely because the baseline commit is unavailable. Malformed state is a validation error under FR-2, not missing history.
- **FR-17 - Change reporting:** Report changed files and the documentation sections they impact for each incremental run. Report which documentation sections were added, changed, or marked "Not Found" on every successful run.
- **FR-18 - Changelog:** Append one entry on the initial successful sync, labeled `Initial documentation sync`, and on later runs with relevant committed changes or generated README updates. Include changed paths, documentation updates, and a UTC date in `YYYY-MM-DD` format; preserve existing entries and sanitize output under FR-25. If neither relevant changes nor generated README updates exist, report "No changes detected" without appending an entry. Tool-generated-only commits excluded by FR-13 shall not create entries. A missing-baseline full rescan shall create an entry if generated output changes; an unavailable baseline alone does not count as a repository change list.
- **FR-19 - Default writes:** Write README, changelog, and baseline updates directly by default, after all required computation and validation have succeeded.
- **FR-20 - Dry run:** Support `--dry-run` to print proposed README and changelog changes as unified diffs, plus a separate baseline SHA transition and the normal run summary, without changing repository, output, or baseline files or creating `--out`. Treat absent output files as empty when rendering diffs; print "No changes detected" when appropriate. A temporary clone is permitted acquisition work and must be cleaned up under FR-3. Sanitize previews under FR-25.
- **FR-21 - Fatal errors:** Handle an empty repository, a missing or invalid path, a non-git directory, missing required files, GitHub 404 responses, and network failures with clear messages and a nonzero exit status rather than an unhandled crash. Missing optional evidence shall yield "Not Found", not a fatal error.
- **FR-22 - Failure preservation:** Fatal errors shall leave existing target files unmodified and leave no partial newly generated output. Compute and validate all planned changes before writing; write-time failure handling must also preserve the all-or-nothing outcome for README, changelog, and sync state.
- **FR-23 - Network retries:** Retry transient network errors and HTTP 5xx failures up to three times after the initial attempt, waiting 1, 2, and 4 seconds respectively, without jitter. Do not retry HTTP 403 or 429 rate-limit errors; report a clear rate-limit message. Report permanent failures such as HTTP 404 clearly without classifying them as transient. Use at most four attempts for an operation, including clone operations when their failure is transient; do not expose raw git or HTTP responses in messages.
- **FR-24 - Environment variables:** Never read `.env` or `.env.*` files except files whose exact basename is `.env.example`; also skip private-key files with `.pem`, `.key`, or `.p12` extensions. Parse only variable names on assignment left-hand sides in `.env.example`, allowing optional `export`; do not retain values. Recognize literal names in `process.env.X`, `process.env["X"]`, `os.environ["X"]`, `os.environ.get("X")`, `os.getenv("X")`, `System.getenv("X")`, `os.Getenv("X")`, and `os.LookupEnv("X")`, accepting either quote style. Do not evaluate dynamic expressions. Emit unique names matching `[A-Za-z_][A-Za-z0-9_]*` in ascending order, never their values. If none are found, output "Not Found".
- **FR-25 - Secret protection:** API keys, tokens, passwords, and environment-variable values shall never appear in tool-produced documentation, changelog entries, summaries, previews, warnings, or errors. Use a single deterministic sanitizer on all emitted evidence, including paths and names: replace PEM private-key blocks, URL user-info, bearer credentials, GitHub tokens prefixed `ghp_`, `github_pat_`, `gho_`, `ghu_`, `ghs_`, or `ghr_`, AWS access-key IDs prefixed `AKIA` or `ASIA`, and values in case-insensitive assignments to keys containing `secret`, `token`, `password`, `passwd`, `api_key`, or `apikey` with `[REDACTED]`. Redact assigned values in environment-reference expressions, and reject credential-bearing input URLs. Do not emit raw source, manifest script bodies, environment assignments, or raw exception messages; only approved extracted fields and sanitized diagnostics. If a candidate cannot be safely extracted, output "Not Found" rather than echoing it. Existing manual destination content remains untouched, even if it contains sensitive text; do not reproduce it in console previews, including diff context. Pattern matching does not certify that a repository is secret-free; do not claim it detects every arbitrary, unlabeled secret.

## Non-functional requirements

- **NFR-1 - Performance:** Scanning, diffing, sanitization, and generation shall complete in under 30 seconds for repositories containing up to 500 eligible tracked files. Exclude full GitHub clone time, output writes, and temporary-directory cleanup from this measurement. The reproducible acceptance benchmark is three consecutive runs, each under 30 seconds, on Linux x64 with 4 logical CPUs, 8 GiB RAM, SSD storage, and Node.js 24, using a local deterministic 500-file fixture with each file at most 16 KiB, all four supported stacks, and 50 committed changed files. Time with a monotonic clock; retain the fixture and timing results in tests. No fixed latency is guaranteed for arbitrarily large individual files.
- **NFR-2 - File counting:** Scan and count tracked files only, excluding `.git`, `node_modules`, `dist`, files matched by committed `.gitignore` rules (even if tracked), and files excluded under FR-5, FR-13, or FR-24. Use HEAD's ignore rules, not dirty working-tree rules. For more than 500 eligible files, warn and continue scanning all eligible files without a 30-second guarantee; never silently truncate the scan.
- **NFR-3 - Compatibility:** Run from the CLI on Windows, macOS, and Linux using Node.js 20 or later. The v1 CI matrix shall run tests on all three platforms using the latest available patch releases of Node.js 20, 22, and 24. Other Node.js versions at or above 20 are supported on a best-effort basis, without an additional v1 CI gate.
- **NFR-4 - Coverage:** Vitest coverage shall be at least 80% for each of lines, branches, functions, and statements. Tests shall include successful behavior and failure or "Not Found" cases for every new function, as required by the project instructions.
- **NFR-5 - Determinism:** For identical repository evidence and options, extraction and README generation shall produce identical results. No AI API calls are permitted. Changelog dates are time-dependent metadata, not inferred repository facts.
- **NFR-6 - Validation and safety tests:** Automated tests shall verify invalid input and output-collision rejection, committed-only extraction despite dirty working-tree content, full-clone incremental URL runs, output identity checks, clone cleanup, manual-content preservation, partial and malformed markers, section-impact rules, generated-only change suppression, dry-run non-modification, missing-baseline fallback, initial changelog entries, exact retry delays and limits, rate-limit non-retry, every listed secret pattern and environment syntax, symlink rejection, and file preservation after fatal failures including write-time failures. Use synthetic secrets, mock retry clocks, and an injected UTC clock for date tests.
- **NFR-7 - Implementation constraints:** Use strict-mode TypeScript, Node.js ESM, commander for the CLI, simple-git for git operations, zod for validation, and Vitest for tests, as specified by the project instructions.

## Assumptions and decisions

### Confirmed decisions

- V1 supports local repositories and public GitHub repositories, including optional GitHub branch selection; private repositories are excluded.
- GitHub input is full-cloned into a temporary directory on every run, without history depth limits or filtering. No history-deepening step is needed; unavailable baselines still trigger the FR-16 fallback. Temporary clones are removed on success and handled failure.
- The four supported stack families may coexist in one repository; unsupported stacks are not guessed.
- Extraction is deterministic and template-based. The explicit setup-command mappings are approved rules, not permission to infer other commands.
- README marker boundaries define tool ownership. Existing unmarked content remains untouched, even when generated sections are appended.
- Only committed changes are synchronized. A dirty working tree produces a warning and is not a source of documentation evidence.
- `.docsync.json` records the successful baseline; absent or unavailable history causes a full scan, with a warning for an unavailable recorded commit.
- Normal runs write directly; dry runs preview without persistent output changes. Fatal failures must not leave partial updates.
- **Evidence selection:** Use root-before-nested manifest ordering and fixed manifest priority for names and descriptions (FR-7/FR-8). Project Name falls back to the first manual README H1, then "Not Found". Purpose falls back to the first manual prose paragraph; Usage falls back to the first case-insensitive ATX `Usage` section. Only committed README content outside generated markers supplies evidence. Python setup without `requirements.txt` is "Not Found". Nested commands are labeled with their working directories.
- **Output layout:** URL runs require `--out`, containing only the three generated artifacts and persistent URL/branch/SHA state. Reject unrelated nonempty destinations; reuse only matching state, preserving manual content. Seed first-run documentation from the repository. Dry runs use sanitized unified diffs plus a baseline transition and create no persistent output (FR-4/FR-14/FR-20).
- **Ownership and impact:** Use the seven canonical marker names in FR-11. Reject malformed or duplicate markers before writing; append missing marked sections even when manual headings exist. Apply the explicit impact mapping in FR-13, taking the union of affected sections and both sides of renames.
- **History and tracking:** Log an initial sync with a UTC `YYYY-MM-DD` date. Ignore sync state, changelog files, and generated-only README changes as source changes; advance the baseline on successful no-change runs without appending repetitive entries (FR-13/FR-14/FR-18).
- **Security details:** Skip environment-value files except `.env.example`, private-key files, and symlinks; never cross repository boundaries. Recognize only the literal environment-reference forms listed in FR-24. Sanitize all emitted evidence with FR-25's fixed patterns and conservative extraction, never echo raw errors or manual diff context, and never describe pattern matching as a complete secret audit. Preserve manual destination content rather than rewriting it.
- **Retries and dates:** Allow three retries after the initial request, at 1, 2, and 4 seconds with no jitter; never retry 403/429 or permanent errors. Use UTC calendar dates, injected clocks, and mocked delays in tests.
- **Performance and compatibility:** Use the explicit 500-file, three-run Linux benchmark in NFR-1. Warn and continue above 500 eligible files without truncation or a time guarantee. Test Windows, macOS, and Linux against Node.js 20, 22, and 24; later versions are best-effort until added to CI.

## Out of scope

- Multi-repository batch runs.
- A web UI.
- API reference generation from code comments.
- Private GitHub repository access.
- AI-based generation or AI API calls.
- Remote commits, pushes, or pull requests.
- Synchronizing staged, unstaged, or untracked content.
- Detecting additional stack families beyond the four explicitly supported families; unknown stacks are reported as "Not Found".
